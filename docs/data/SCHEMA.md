# Processed data schema

All tables live under `data/processed/` as UTF-8 CSV with a header row. Column
names are snake_case. Money is a decimal string with two places in USD. Dates
are ISO `YYYY-MM-DD`. Booleans are `true` or `false`. Empty string means null.

Two kinds of tables:

- **Parsed** tables are generated by `data/pipeline/` from the raw files and
  are never edited by hand (`base_rates.csv`).
- **Curated** tables are transcribed from the documents. Every row carries a
  citation (`source_file`, `source_ref` or `source_page`, `source_quote`) and
  the test suite checks that the quote, including the amount, appears on the
  cited page of the cited file.

`year` everywhere is the price-list label: the list prices that took effect in
January of that year (USPS 2023 uses the July 9 2023 tables; FedEx 2027 is the
forward year). `effective_date`, `effective_from` and `effective_to` record the
actual dates, because some rules change inside a year.

## Layout

Each carrier's pipeline writes only to its own directory, so parsers can be
built independently and never conflict:

```
data/processed/
  services.csv                 shared, curated
  zone_from_distance.csv       shared, curated
  usps/  base_rates.csv  surcharges.csv  fuel_surcharge.csv  announced_increase.csv  dim_weight.csv  exceptions.csv
  ups/   (same files)
  fedex/ (same files)
```

The backend loads every carrier directory and concatenates tables of the
same name. A carrier with no fuel surcharge ships a header-only file.

### Invariants: warnings, with every exception documented

The invariant checks never silently pass. Each anomaly is either listed in the
carrier's `exceptions.csv` (then the test emits a warning) or it fails the test.
This forces every oddity in a rate card to be written down.

Checks:

- For each (carrier, service_id, rate_card, year): every zone in the carrier's
  range is present with the same set of weight steps, strictly increasing,
  with no gaps up to 70 lb.
- Within a zone, price is non-decreasing with weight. Within a weight step,
  price is non-decreasing with zone.
- Prices have at most two decimals and no float artifacts (e.g. `15.999000000000001` in a weight label).
- Every `source_file` exists in `data/raw/manifest.csv`.

`exceptions.csv` (curated, per carrier):

### Golden samples

`data/tests/golden/<carrier>_<year>.csv` holds hand-checked cells with the
`base_rates.csv` columns plus `checked_by` (person or "agent" plus date) and
`source_ref`. The parsed output must match every golden cell exactly.

Mandatory cells for each (service_id, rate_card, year), because column and
page shifts in the PDFs corrupt exactly these corners:

1. heaviest weight step (70 lb) in the farthest zone
2. heaviest weight step in the nearest zone
3. lightest weight step in the farthest zone
4. at least two interior cells on different pages or sheets of the source

Minimum five cells per (service_id, rate_card, year).

Peak rules apply only when the dashboard's peak toggle is on. Rules with
`address_type` `residential` or `commercial` apply only to parcels of that kind.
Delivery area rules apply when the parcel's `delivery_area` is `das` or
`extended`. `additional_handling_packaging` rules apply when the parcel is
flagged `nonstandard_packaging` (UPS and FedEx: non-corrugated or cylindrical
packaging; USPS from 2026: tubes or rolls, cans, wooden or metal boxes, liquids
in glass).

### Engine tests for fuel

The rate engine applies the fuel percent to the base rate plus every applied
surcharge whose `fuel_applies` is `true`, and to nothing else. Tests use
synthetic rows: one surcharge flagged `true`, one flagged `false`, a known
percent, and assert the fuel line item equals `percent × (base + flagged)` to
the cent, that the slider override replaces the yearly default, and that USPS
quotes carry no fuel line.

## Rules that change over time

Every parameter that can move a parcel's price is stored per year and per
effective window: base rates, surcharge amounts and thresholds, fuel defaults,
dimensional-weight divisor and threshold. The engine takes an `as_of` date
(default: the year's January effective date) and never hardcodes a value.

`uv run python -m data.pipeline.report_changes` diffs consecutive years of
every curated table and writes `docs/data/RULE_CHANGES.md`: one line per
parameter that changed, with old and new values and the citation. The parser
agents must populate every year so this report is complete, and the report is
reviewed before the engine is built so year-over-year comparisons account for
every change, not only base rates.
